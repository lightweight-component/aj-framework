# aj-fileupload 待修复问题

本文记录当前仍未解决的安全、稳定性和设计问题，按优先级排序。已完成的 MIME 映射比较、`NO_CHECK` 空指针修复、`Locale.ROOT`
处理、规则集合不可变及视频 `ftyp` 测试修复不再列入。

## P0：公开上传场景必须先处理

### 1. 默认配置允许任意文件落盘

`FileUploadConfig` 默认 `DetectType.NONE`，扩展名白名单为空。也就是说，调用方若没有显式配置，任意非空文件都可以保存。若该目录被
Nginx、Tomcat 或对象存储公开访问，可能造成脚本、HTML、恶意文档等不受控文件暴露。

建议：

- 默认拒绝未声明允许类型的上传，或要求显式设置危险开关才允许任意文件；
- 生产环境要求显式配置上传根目录、允许扩展名和检测类型；
- 上传原始文件先保存到非 Web 根目录或隔离区，不要直接静态公开。

### 2. 本地落盘存在符号链接竞态和覆盖风险

`FileUpload.saveToDisk()` 在检查目标不是符号链接后才调用 `MultipartFile.transferTo()`
。检查和写入之间，具有本地目录写权限的攻击者可以替换目标；`ORIGINAL` 命名策略也会直接覆盖同名文件。

建议：

- 默认仅使用服务端随机文件名；
- 在受控目录创建独占临时文件，写入完成后使用同目录原子移动到最终文件；
- 最终文件使用“不允许覆盖”的创建语义；
- 上传根目录应由应用账户独占写入，不能与不可信用户共享。

### 3. `PermissionCheck` 只告警，不产生安全效果

当前权限扫描只写日志，既不会删除文件执行权限，也不会限制新上传文件的权限。更重要的是，POSIX 目录的 execute
位表示“可进入/可检索目录”，通常是正常且必要的权限，不应当当作“可执行目录”风险。

建议：

- 删除“扫描后即安全”的误导性模型；
- 创建上传目录和文件时主动设置权限，例如目录仅应用账户可写、文件默认不可执行；
- 在部署文档中明确上传目录不可作为脚本执行目录；
- 移除全局 `isAlreadyChecked`，它只检查第一个目录且并发下不可靠。

## P1：应在发布前处理

### 4. 请求体和压缩包资源限制不足

库在拿到 `MultipartFile` 后才比较 `getSize()`，无法阻止 Spring 在解析请求、写临时文件时已经消耗磁盘或内存。ZIP Office
校验虽然限制了条目数和总解压量，但固定允许解压 100 MiB，仍可能被小压缩包放大 CPU 和 I/O 消耗。

建议：

- 在 Spring Multipart 层配置单文件大小、总请求大小、文件数量、临时目录和读取超时；
- 将 ZIP 条目数、单条目大小、累计解压量和校验时间设为可配置项；
- 对大型或不可信文档改为异步扫描，避免占用 Web 请求线程。

### 5. 文件类型校验仍只是初筛

扩展名、客户端 Content-Type 和文件头都不能证明文件“安全”：短魔数可伪造，JPEG/PDF 等可构造 polyglot 文件，旧 Office 的 OLE
头也无法区分 doc/xls/ppt。当前音视频扩展名集合还大于已实现的魔数规则集合，导致部分合法文件会被拒绝。

建议：

- 将魔数检测在文档和 API 中明确标为格式初筛；
- 图片使用真实解码器读取，文档使用受限解析器做结构校验；
- 补齐或收紧音视频扩展名与检测规则，避免“允许但必然校验失败”；
- 需要对外公开下载时，结合杀毒/恶意内容扫描、人工审核或对象存储隔离；
- 当前 MIME 映射依赖操作系统的 `Files.probeContentType`，跨平台结果可能不同，后续应改为库内确定性映射表。

### 6. 文件名和返回 URL 未完全净化

文件名目前仍允许 Windows 特殊名称、冒号（可能触发 NTFS Alternate Data
Stream）、尾随点/空格及双向控制字符。返回结果中的 `originalFileName` 使用客户端原值；返回 URL 直接拼接文件名，未对路径段进行
URL 编码。

建议：

- 存储名始终使用服务端生成的随机安全名称；
- 原始名称仅作展示，保存前进行长度限制、Windows 保留名和危险字符检查；
- 返回展示名时由前端进行 HTML 转义；
- URL 使用逐路径段编码，不直接字符串拼接。

### 7. 下载 API 容易被误用，且仍有竞态窗口

`Download.download(Path, String)` 和 `downloadServlet(HttpServletResponse, File, String)`
接受任意服务端路径，只依赖调用方遵守“可信路径”约定。根目录下载版本虽校验了穿越和真实路径，但校验完成到实际打开文件之间仍存在符号链接替换的竞态窗口。

建议：

- 对外只保留“可信根目录 + 相对路径”的下载入口；
- 任意 `Path` 下载方法改为内部方法，或使用显式危险命名；
- 在可信、应用独占目录中通过不跟随链接的方式打开文件；
- 下载响应增加 `X-Content-Type-Options: nosniff`，并保持 attachment 下载策略。

## P2：设计与可维护性问题

### 8. 注解与反射式上传入口语义不一致

`@FileUploadAction` 声明可用于类和方法，但 `UploadUtils` 只读取方法上的直接注解。它还根据“类 + 方法名 +
固定参数签名”反射查找配置；重构、重载、继承时容易失效，并且工具类不会真正调用 Controller 方法。

建议：

- 要么实现类级注解继承和方法覆盖规则，要么移除 `TYPE` target；
- 优先改为类型安全的配置对象或 Spring Bean 服务；
- 若保留注解，使用 Spring MVC 参数解析器/AOP 在框架层处理，而不是让业务代码传方法名。

### 9. 默认本地目录不适合生产和跨平台

默认值 `c:/temp/uploads` 是 Windows 风格路径，在 Linux 上含义不直观，也可能在应用工作目录创建意外层级。默认 `urlPrefix`
为空，调用方又可能把结果直接交给前端。

建议：

- 不提供生产可用的默认存储目录，要求应用在配置中明确指定；
- 将物理存储路径、访问 URL、是否公开下载拆成独立配置；
- 启动时校验配置，不要等到首个上传请求才失败。

### 10. 兼容性边界尚未说明

当前代码使用 `jakarta.servlet`，并按 Java 17 编译。因此它天然面向 Spring Boot 3+/Java 17+，不能直接用于使用 `javax.servlet`
的 Spring Boot 2.x 应用。

建议：

- 在 README 明确最低 Java 与 Spring Boot 版本；
- 若要支持 Boot 2，需要独立兼容方案或拆分适配层，不要混用 `javax`/`jakarta`。

### 11. 文档和未完成 API 需要收敛

README 目前为空；`ShowUrlPolicy.Policy`、`SendDownload`、空的 `ServletResponse`、未实现的 `FILE_SERVICE`
与 `FILE_SERVICE_API` 会让调用方难以判断哪些能力可用。

建议：

- 补充安装、最小安全配置、错误处理、公开访问风险和下载示例；
- 删除未使用 API，或明确标记为未实现；
- 对未实现存储类型提供扩展接口，而不是枚举后运行时抛异常。

## 测试补充建议

- Windows 文件名：ADS、保留设备名、尾随点/空格、Unicode 双向控制字符；
- 并发写入、同名覆盖、符号链接替换；
- 上传目录在 POSIX 与 Windows 下的真实权限行为；
- MIME 映射在不同操作系统上的一致性；
- 大请求、ZIP 高压缩比和大量 ZIP 条目；
- 下载根目录、符号链接、响应头与文件名编码；
- 真实图片、Office、音频、视频样本的正反例。
