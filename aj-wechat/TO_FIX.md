# aj-wechat 待修复事项

本文记录代码审查发现的问题，按风险和建议处理优先级排序。除非另有说明，以下均未在本次审查中修改源码。

## P0：安全与正确性

### 1. 支付回调未强制验签

`PayCallback`、退款回调和分账回调会直接解密并处理回调数据；虽然已有验签方法，但主流程没有调用。且回调入口接收 `Map`，已经丢失了验签所需的原始请求体。

这会使伪造回调、重放回调有机会被业务当作真实支付结果处理。

建议统一回调入口，接收原始 body 与 `Wechatpay-Signature`、`Wechatpay-Serial`、`Wechatpay-Nonce`、`Wechatpay-Timestamp` 请求头；先校验签名、时间戳与重放，再解密和执行业务。处理时还应在事务内核对商户号、应用、订单号、金额、币种与本地订单状态，并通过数据库唯一约束或状态机保证幂等。

### 2. 私钥缓存会串用不同商户的密钥

`SignerMaker` 使用一个静态字符串缓存私钥。进程中首次加载的私钥会被后续所有商户配置复用，多商户场景将导致签名错误，甚至以错误身份签名。

建议将解析后的 `PrivateKey` 按规范化文件路径或商户号缓存，支持刷新/失效；更简单可靠的方案是由各商户客户端实例持有自己的私钥。

### 3. 平台证书与序列号的匹配逻辑不正确

回调验签代码虽然以平台证书序列号作为缓存键，但实际始终读取同一个配置文件，没有验证该文件证书是否与序列号对应，也未处理平台证书轮换或微信支付公钥。

建议建立“序列号 -> 平台证书/公钥”的可信仓库。遇到未知序列号时按官方机制刷新证书后再验签；证书轮换期间保留有效的旧证书。不要将任意 PEM 文件直接按序列号缓存。

### 4. 微信 API 的错误响应会被误判为成功

`PayUtils.postMap()` 判断错误码时使用了 `"code "`（末尾多了空格），正常的 `code` 字段无法命中，调用方可能把失败响应当作成功处理。

建议修正字段判断，并按 HTTP 状态码、`code`、`message` 统一构造明确的成功/失败结果；为微信 API 的成功、业务错误和非 JSON 错误响应各补一项离线测试。

### 5. 普通 API 响应没有验签能力

`Get`、`Post` 仅返回反序列化后的 `Map`，丢弃了响应头和原始响应体，无法校验微信支付 API 的响应签名。

建议将底层 HTTP 返回值建模为包含状态码、原始 body 与 headers 的对象，先验签再反序列化。账单下载响应属于例外，应按官方规则校验下载文件哈希值。

## P1：高优先级可靠性与安全改进

### 6. 日志可能泄露密钥、令牌、密文和业务数据

当前签名、支付工具类、回调解密、公众号消息和小程序二维码相关代码会记录或打印 Authorization、访问令牌、原始报文、密文、解密后的平台证书等敏感信息；测试中也存在密钥和商户信息。

建议删除这些日志，或仅记录脱敏后的请求 ID、商户号尾号、订单号尾号、状态码与错误码。严禁记录私钥、完整 token、签名原串、密文、解密结果和客户隐私数据。

### 7. 账单下载 URL 可被任意传入

`BillService.billDownload(String url)` 直接请求外部传入的 URL，并沿用支付签名请求头，存在服务端请求伪造（SSRF）和签名请求头泄露风险。

建议只接受刚从微信账单申请接口获得的结构化下载地址；校验 HTTPS、固定微信支付主机名、允许路径和禁止重定向。下载后校验官方返回的文件哈希值。

### 8. 金额处理使用 `double` 与 `int`

`PayUtils.changeY2F(double)` 会受到浮点精度、格式化本地化的影响；`bigDecimal2Fen` 使用 `intValue()`，金额较大时可能溢出。

建议金额统一使用最小货币单位的 `long`，或以 `BigDecimal` 按明确舍入规则转换后使用 `longValueExact()`；拒绝超出范围和不符合小数位规则的输入。

### 9. 商户订单号不具备可验证的唯一性和幂等语义

当前订单号由分钟级时间和随机字符组成，无法保证跨实例、跨重试的唯一性，也不能将重复请求稳定地映射到同一笔支付。

建议由业务订单表生成并加唯一索引，重复支付请求复用同一 `out_trade_no`；若确需生成器，使用数据库序列、雪花算法或 UUID，并保留长度和字符集约束。

### 10. URL 参数直接拼接，未进行编码与稳定排序

多个接口直接字符串拼接 query，`mapToQueryString` 也不编码参数。特殊字符会破坏请求，签名场景还会产生不稳定结果。

建议使用 URI 构造器完成 UTF-8 编码；签名参数按协议要求排序并使用同一份规范化结果。

### 11. 分账订单状态使用静态 `HashMap`

`ProfitSharingApiService.ORDER_PROFIT` 是公开、无界、非线程安全的静态内存表。它在多实例部署时不一致，重启即丢失，并可能造成内存持续增长。

建议移除该状态，改由数据库订单状态和唯一约束保证；若只是短期缓存，也应使用有界并发缓存且不能作为最终业务依据。

### 12. 支付相关服务允许缺失配置后继续运行

若干服务使用 `@Autowired(required = false)` 注入商户配置，配置缺失时会在真正发起支付时产生空指针，而不是在启动阶段清晰失败。

建议使用 `@ConfigurationProperties` 加校验，按配置条件创建 Bean；缺少必要商户号、私钥、证书等时给出明确启动错误或禁用相应能力。

## P2：设计、配置与可维护性

### 13. 自动配置不完整

`WechatConfiguration` 主要依赖包扫描，部分配置代码被注释，条件开关默认禁用，服务自身又依赖 `@Value`。作为 Starter 时，使用者难以理解哪些 Bean 会创建、缺少配置时会发生什么。

建议整理为正式的自动配置：定义统一的 `ConfigurationProperties`、条件注解、默认值与校验，注册自动配置声明文件，并在 README 给出最小可运行配置。

### 14. 公众号 token 与 JS-SDK 初始化有可靠性问题

`OpenAccount` 将 `appId` 和 `secret` 拼接在 URL 中；每次初始化都新建 `Timer`，无法关闭；刷新间隔固定且没有失败退避。`init(HttpServletRequest)` 未处理空 User-Agent，协议判断使用远端端口，且 JS-SDK ticket 当前未实际获取。

建议改用可关闭的调度器或 Spring 调度任务，按真实 `expires_in` 提前刷新，失败采用退避和抖动；使用 HTTP 参数构造器，避免 URL 日志泄露；正确处理反向代理协议头和空请求头，并实现 ticket 获取、缓存与刷新。

### 15. `TokenAutoRefresher` 可重复调度且失败后不可恢复

重复调用 `start` 或手动刷新会叠加定时任务；供应函数或回调抛异常后可能不再安排下一次刷新；无效过期时间会造成约每秒循环。

建议保存并取消 `ScheduledFuture`，保证单实例单任务；记录令牌获取时间和实际有效期，限制最短调度间隔，在失败时使用受控退避重试，并提供 `close()`/销毁钩子。

### 16. 公众号客服消息实现缺少超时、校验和约束

每次调用都新建 `RestTemplate`，未设置连接/读取超时；发送后没有统一检查微信错误响应；也未限制 `mpnews`、`miniprogrampage` 等互斥消息体。

建议注入共享的 HTTP 客户端并配置超时；统一解析和校验错误响应；在发送前验证消息类型与消息体一一对应，移除 `System.out` 输出。

### 17. 小程序二维码接口仍是半成品

`MiniAppService.qrCode` 仅打印请求 JSON，实际 HTTP 调用被注释；JSON 由 `String.format` 拼接，特殊字符会产生非法 JSON 或注入错误字段。

建议使用 JSON 序列化器构造请求，完成真实调用并返回二进制二维码或可读错误对象，同时设置超时与响应大小限制。

### 18. 文档与兼容性说明不足

README 缺少配置项、模块能力、回调验签/幂等要求、账单下载限制、异常模型和测试方式说明。当前构建使用 Jakarta Servlet 与较新的 Java/Spring Boot 依赖，不能自然等同于 Boot 2/`javax` 兼容。

建议明确发布坐标、最低 Java 与 Spring Boot 版本；如需兼容 Boot 2，应拆分兼容层或提供对应版本产物，避免在同一产物中混用 `javax` 与 `jakarta`。

### 19. 现有测试依赖真实网络和本机环境

部分测试会访问真实微信接口或外部 IP，且包含硬编码密钥、商户信息和绝对文件路径。它们会导致构建不稳定、可能泄露凭据，并且在离线环境中长时间阻塞。

建议将单元测试改为 MockWebServer/WireMock 等本地模拟服务；测试密钥放入专用测试资源或环境变量，不提交真实凭据；真实联调测试单独使用 profile，默认 Maven 测试不执行。

## 建议修复顺序

1. 先完成回调验签、回调幂等和订单金额核验，再修正 API 错误码判断。
2. 修复私钥/平台证书管理和普通 API 响应验签能力。
3. 清理敏感日志，限制账单下载 URL，改正金额与订单号处理。
4. 重构配置、HTTP 客户端和 token 调度，补齐半成品接口。
5. 将测试改为完全离线，并补充使用文档与兼容性边界。
